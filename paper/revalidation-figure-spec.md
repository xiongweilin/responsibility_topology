# Paper 3 Figure Architecture

Status: paper-only visual specification. No formal semantics.

The manuscript should use **two primary figures**. The first explains the research object; the second explains the repair interfaces. The hypergraph is subordinate to these figures rather than the paper's visual identity.

## Figure 1 — Persistent History and Typed Currentness Across Revision

### Purpose

Make the paper's strongest conceptual object visible in one glance:

```text
persistent historical identity
+
typed, non-monotone current responsibility.
```

### Axes

Horizontal lifecycle axis:

```text
formation / qualification
        -> challenge
        -> refresh
        -> repair
        -> final refresh
```

Vertical semantic layers:

```text
historical plane
warrant currentness
license currentness
context currentness
```

### Canonical content

```text
                           formation /       challenge         refresh          repair            final refresh
                           qualification

HISTORICAL PLANE          p -> d; L; Adopt provenance ================================================
                          identity/referents remain canonical across modeled stages

WARRANT CURRENTNESS       LIVE + PLACED  -> SUSPENDED/PENDING -----------------> requalified -------- usable
                                 |
                                 | support dependency
                                 v
LICENSE CURRENTNESS       BaseCurrent     -> review/stale ---------------------> BaseCurrent -------- current
                                 |
                                 | activation responsibility
                                 v
CONTEXT CURRENTNESS       Grounded        -> grounding fails -> inactive ------> reactivated -------- Grounded
```

### Figure rules

1. The historical row must visually continue across every column without appearing to be regenerated by repair.
2. The three lower rows must be visibly distinct; do not merge them into one `valid` lane.
3. The arrows `Usable -> BaseCurrent -> Grounded` denote modeled dependency implications, not definitional equality.
4. The target's placement nuance may be explained in the caption/text: suspension alone can withdraw usability even where target placement is retained.
5. Do not put the repair hypergraph into this figure. Its job is to establish the object of study before combinatorics appear.
6. Caption must use **state-indexed currentness**, not time-indexed, unless discussing an informal lifecycle reading.
7. Caption must not claim an explicit end-to-end history theorem; use stage-local/compositional preservation language.

### Caption draft

> **Figure 1: Persistent history and typed currentness across revision.** Canonical warrant and Adopt referents remain recorded across the modeled challenge, refresh, and repair stages, while warrant usability, license `BaseCurrent`, and context `Groundedness` may weaken and later be re-established. The three currentness rows are distinct state relations; dependency arrows show how loss can propagate, not predicate identity.

## Figure 2 — Repair Selection, Semantic Effectiveness, and Reachable Execution

### Purpose

Prevent readers from collapsing the four repair judgments:

```text
model
!= selection
!= effectiveness
!= execution.
```

### Canonical content

```text
             externally supplied / extracted finite model
                              |
                              v
                        RepairProblem
                              |
                              | unresolved responsibility cuts
                              v
                         RepairSet
                              |
                              | unordered selection
                              | (hitting-set condition)
                              v
                      RepairRealization
                              |
                              | semantic effectiveness certificate
                              v
                     RevalidationTrace
                              |
                              | ordered proof-carrying execution
                              v
                    reachable restored state
```

Side boundary:

```text
represented-cut necessity: EveryRepairCutNecessary
extraction completeness: not established
```

### Hypergraph inset

Use the running example only as a small inset:

```text
Ow <- {a,b}
Ol <- {l}
Oc <- {c}

X1 = {a,l,c}
X2 = {b,l,c}
```

Label explicitly:

```text
two abstract inclusion-minimal repair sets
one directly demonstrated reachable branch
```

### Figure rules

1. `RepairSet` must never visually point straight to “restored” without passing through `RepairRealization`.
2. `EveryRepairCutNecessary` must sit beside the represented model, not after execution as if it were a runtime check.
3. Extraction completeness must remain outside the certified pipeline; use a dashed/open boundary if rendered graphically.
4. `RevalidationTrace` is ordered; `RepairSet` is not.
5. Avoid “minimal frontier”; use **inclusion-minimal repair set**.
6. Do not depict `X2` as reachable unless a future theorem establishes that fact.

### Caption draft

> **Figure 2: Repair responsibility interfaces.** A finite `RepairProblem` represents unresolved responsibility cuts; `RepairSet` selects actions that hit those cuts but does not establish their effects. `RepairRealization` supplies semantic effectiveness, and an ordered `RevalidationTrace` supplies proof-carrying execution. Necessity of represented cuts is an additional premise, while completeness of the extracted model remains outside the current theorem surface.

## Visual hierarchy

Figure 1 should appear before the first repair definition and receive more visual space than Figure 2.

Recommended manuscript order:

```text
Introduction
-> state model
-> Figure 1
-> running example / challenge + refresh
-> repair model
-> Figure 2
-> T2 / T3
-> adequacy boundary
-> T4 reachable realization
```

This order ensures that readers encounter hitting sets only after they understand what typed currentness is being repaired.
